Admin Queue System - Faction Designer Integration

This prompt documents the faction designer queue processing system.

═══════════════════════════════════════════════════════════════════════════
MANDATORY: UPDATE REQUEST STATUS WHEN WORK IS COMPLETE
═══════════════════════════════════════════════════════════════════════════

CRITICAL RULE - YOU MUST FOLLOW THIS EVERY SINGLE TIME:

When you finish work on ANY request (build, extract, bug, menu, etc.):

1. **Update the terminal log** with your summary and cost:
   ```bash
   echo "Your work summary" > /tmp/summary.txt
   python3 designer-admin.py tlog-summary <request-id> /tmp/summary.txt
   python3 designer-admin.py tlog-cost <request-id> <usd-cost>
   ```

2. **Update the request status to "done"**:
   ```bash
   python3 designer-admin.py request-status <request-id> done
   ```

DO NOT SKIP STEP 2. If you only update the terminal log but forget to update the
request status, the request will show as "PENDING" forever in the admin console,
even though the work is complete. This is THE MOST COMMON MISTAKE.

**When to mark status="done":**
- You completed the work successfully
- You added summary and cost to terminal log
- The .reply file exists in ~/.cw-admin-queue/done/

**When to mark status="cancelled":**
- The request was a duplicate or test
- The user explicitly asked to cancel it
- The request is invalid/impossible

NEVER leave a request in status="notified" or "open" after you finish working on it.

═══════════════════════════════════════════════════════════════════════════
20-MINUTE / 3-TRY LIMIT - STOP AND HAND OFF, DO NOT GRIND
═══════════════════════════════════════════════════════════════════════════

If you cannot solve this request within 20 minutes, OR you have tried and
failed 3 times (same error repeating, same approach not working), STOP.
Do not keep looping on the same approach.

Instead:
1. Take what you have done so far (partial fix, diagnosis, files touched).
2. Write a clear, short summary: what you tried, what worked, what is still
   broken, and your best guess at what to try next.
3. End your reply with that summary. Do not keep working past this point.

This hands the task to the next tier automatically (this queue escalates
Haiku -> Sonnet -> Opus on failure). The next agent that picks this up -
whether it is a Sonnet or an Opus run - has these SAME instructions: if IT
also can't solve it in 20 minutes or 3 tries, it stops and hands off the
same way, one tier up. Opus is the last tier; if Opus also hits the limit,
summarize plainly for the owner instead of continuing to retry.

SILHOUETTE GENERATION
═══════════════════════════════════════════════════════════════════════════

Designers can request silhouette generation from their custom uploaded map images.
A silhouette is a flat white version of the map image with transparent background,
used on faction cards.

WHEN YOU RECEIVE A SILHOUETTE GENERATION REQUEST:

The request will include:
- Unit name
- Faction name
- Map image ID
- Map image URL (use this to download the source image)
- Unit ID
- Faction ID

STEPS:

1. **Download the source map image**:
   ```bash
   cd /tmp
   python3 ~/Claude-Projects/cthulhu-wars-tools/tickers/designer-admin.py image <imageId>
   # This downloads and converts to PNG, prints the local path
   ```

2. **Generate the silhouette** using ImageMagick or Python PIL:
   ```bash
   # Method 1: ImageMagick
   convert input.png -channel RGB -negate -colorspace gray -negate \
     -threshold 50% -fill white -opaque black output-silhouette.png

   # Method 2: Python PIL (better for preserving transparency)
   python3 << 'EOF'
   from PIL import Image
   import sys

   img = Image.open('input.png').convert('RGBA')
   pixels = img.load()
   for y in range(img.height):
       for x in range(img.width):
           r, g, b, a = pixels[x, y]
           if a > 0:  # Not transparent
               pixels[x, y] = (255, 255, 255, a)  # White, preserve alpha
   img.save('output-silhouette.png')
   print('✓ Silhouette generated')
   EOF
   ```

3. **Upload the silhouette**:
   ```bash
   cd ~/Claude-Projects/cthulhu-wars-tools/tickers
   python3 designer-admin.py upload /tmp/output-silhouette.png
   # Prints the new image ID
   ```

4. **Attach to the unit** (patch the faction design):
   ```bash
   # Create patch operation. Op is "set" (not "replace"); path is dot-separated with the
   # row id used directly in the path (no array index, no leading "/"):
   echo '[{"op":"set","path":"units.rows.<unitId>.silhouette","value":"<newImageId>"}]' > /tmp/patch.json
   python3 designer-admin.py patch <factionId> /tmp/patch.json
   ```

5. **Verify the silhouette visually** (required):
   - Use the Read tool on /tmp/output-silhouette.png and LOOK at it: flat white
     shape, transparent background, same outline as the unit, no colored pixels,
     no black box.
   - After the faction is rebuilt / deployed with --assets: open a game with the
     faction, open the faction card (example E2), screenshot `.faction-table`, and
     check V10 - the silhouette shows on the right unit row and looks correct.
   - If the faction has not been rebuilt yet, say "silhouette attached in designer;
     NOT yet visible in game until rebuild" - do not say it is done in game.

6. **Report completion** with a summary of what you did, the new silhouette image ID,
   and the screenshot paths you checked.

EXAMPLE WORKFLOW:

```bash
# 1. Download source
IMG_PATH=$(python3 designer-admin.py image abc123xyz)

# 2. Generate silhouette
python3 << 'EOF'
from PIL import Image
img = Image.open("$IMG_PATH").convert('RGBA')
pixels = img.load()
for y in range(img.height):
    for x in range(img.width):
        r, g, b, a = pixels[x, y]
        if a > 0: pixels[x, y] = (255, 255, 255, a)
img.save('/tmp/silhouette.png')
EOF

# 3. Upload
NEW_ID=$(python3 designer-admin.py upload /tmp/silhouette.png | tail -1)

# 4. Attach (op "set", dot-separated path, row id used directly — not RFC-6902)
echo "[{\"op\":\"set\",\"path\":\"units.rows.unit123.silhouette\",\"value\":\"$NEW_ID\"}]" > /tmp/patch.json
python3 designer-admin.py patch fac456 /tmp/patch.json
```

SILHOUETTE GENERATION
═══════════════════════════════════════════════════════════════════════════

Designers can request automatic silhouette generation from their uploaded map images.
A silhouette is a flat white version of the unit image with transparent background.

WHEN REQUESTED:
- Designer clicks "Generate Silhouette" button in Units section
- Button only appears when designer has uploaded a unique map image (not from CW/Necro library)
- Request comes through as a bug report type with text like:
  "Generate silhouette for unit [name]. Convert map image to flat white silhouette..."

HOW TO GENERATE:
1. Read the original map image using the provided image ID
2. Keep the transparent background
3. Replace ALL colored pixels (any non-transparent pixel) with solid white (#FFFFFF)
4. Save as new image with "-silhouette" suffix
5. Upload the silhouette image to the designer
6. Update the unit's silhouette field with the new image ID

TECHNICAL APPROACH:
- Use image processing tools (ImageMagick, PIL, etc.)
- Command example: `convert input.png -alpha extract -negate output.png`

Multi power Spellbooks:
Spellbooks with multiple powers on 1 spellbook side should be treated as a single spellbook. This includes but is not exclusive to:
- Faction card spellbook / SBR slots- no faction should EVER have more than 6 SBR/ SB slots on its faction card, unless you are explicitly told otherwise
- SBRs and availability of the powers- completing a single SBR can earn you a SB with 2 powers. That is still ONE spellbook. You earn BOTH powers at once.

Multi sided Spelllbooks

Spellbooks with 2 spellbook sides that both have powers should be treated as 2 spellbooks, but generally 2 spellbooks that are connected and can be swapped out one for the other, per the explicit rules of that spellbook. NOT as 2 spellbooks that can each be taken independently. Leverage how the neutral spellbook "recriminations" works to code the swap out, but make sure it is strictly applied so that only "sides" of the same spellbook can be swapped out via this faction's swapping mechanism. (Recriminations will still apply and should still work- but will apply to swapping in a totally separate spellbook, not a separate "side" of the same spellbook").

Spellbooks that have 2 sides with powers can have a 3rd "face down" side. If the spellbook power says to flip it "face down" after use, it is either a use once power, or a use and recharge power. Its own rules should determine which. For a "use once" power, once used, it is blocked for the rest of the game. See opener of the way's "dragon ascending" for an example of this, and to copy its code. For a "use and recharge" spellbook, see any of daemon sultans spellbooks, to copy their code. They are flipped face down when used, and are flipped face up (recharged) in the doom phase. For a different "recharge" mechanism, see the Library Times associated with the Library at Celaeno Map. They can be "recharged" by spending a token associated with that map (silence tokens).

For a spell book with 3 total sides (2 with powers, one the "face down"/ powerless side), see the spell book rules for when (if) it is "recharged" whether it goes back to side 1 or side 2.

## FACTION DESIGNER - SECTIONS AND DATA STRUCTURE

A faction design has these sections (each section = one collapsible accordion in the UI):

### 1. META Section
- Faction name, acronym, color
- Stability setting (experimental / stable)
- Admin notes (private, only admins see these)

### 2. UNITS Section
Each unit is a row in a table with:
- **Basic**: name, type (Cultist/Monster/Terror/GOO/Elder God), cost, combat
- **Images**: map image (URL or upload), silhouette image (white SVG for faction card)
- **Special Ability**: checkbox, ability name, ability type (dropdown), ability text
- **Spellbook Requirements**: which spellbooks are needed to recruit this unit
- **Related Spellbooks**: spellbooks that unlock when recruiting this unit
- **Notes**: free-text field (often contains spellbook names or ability descriptions)

**Validation rules for units:**
- Name required
- Type required
- Cost required (number)
- Combat required for non-Cultists
- If special ability checked: ability type AND ability text required
- Map image required (except "Other Custom" types)
- Silhouette optional

**Buttons for units:**
- Add Unit (creates new empty row)
- Delete Unit (removes row)
- Generate Silhouette (creates white silhouette from map image - only enabled if unit has custom/unique map image)
- CW/Necro button (choose from library of official faction images)

### 3. SPELLBOOKS Section
Each spellbook is a row with:
- **Basic**: name, type (11 types: Start of Battle, Battle, Desecrate, Instant, etc)
- **Cost**: how much Power to buy it
- **Requirements**: numeric (how many of X type), glyphs, specific other SBs
- **Effect**: fixed numeric effect (like "+1 Combat") and effect text
- **Text**: full rules text
- **Two-sided**: checkbox, if checked adds Side B with separate name/type/cost/text
- **Dual powers**: checkbox, if checked adds Power 2 fields (one SB = two abilities)
- **Earned by SBR**: checkbox (SB Ritual earns this for free)
- **Replaceable**: checkbox (can be replaced by SB Ritual)

**Validation rules for spellbooks:**
- Name required
- Type required
- Cost required
- Text required
- If two-sided: Side B name/type/cost/text all required
- If dual powers: Power 2 name/type/text all required

**Special spellbook logic:**
- "All 2-sided" checkbox at top: makes EVERY spellbook two-sided at once
- Each spellbook can be individually toggled back to 1-sided
- Dual powers is separate from two-sided (can have dual-power single-sided SB)

### 4. UNFACTIONED ABILITIES (UFAs) Section
Passive abilities that apply to the whole faction, not tied to a unit or SB.
- Name, ability type, text
- 1-2 UFAs per faction is typical
- Example: "Cultists are Undead" (global rule)

### 5. INTERACTIONS Section
Special rules for how this faction interacts with maps or other factions.
- Map interactions: "On Yuggoth map, Cultists can fly"
- Faction interactions: "When playing against Yellow Sign, X happens"

### 6. SIMPLE UPDATE Section
Quick-update rows for common changes (images, costs, combat values).
Used for mass updates without editing full JSON.
- Numeric fields (costs, combat, counts)
- Text fields (names, descriptions)
- Image fields (map images, silhouettes)

### 7. CUSTOM LOGIC Section
Free-text notes for special coding requirements that don't fit the structured form.
Example: "Cthulhu's Eternal Lies requires custom overlay to show regeneration counter"

- Required fields get red outline if empty and you try to submit
- Dropdown fields validate that selection is from allowed list
- Numeric fields validate that value is a number
- Cannot submit build request if required fields are missing

**Missing fields tracking:**
- `window.Rules.checkMissing(faction)` returns array of missing field paths
- Example: `["units.rows.abc123.abilityType", "spellbooks.rows.xyz789.cost"]`
- Red outline applied to fields in this list via CSS class `sx-missing`

**Build button states:**
- Green "Build" button: all validation passed, ready to submit
- Grey "Build" button: validation errors present, shows "Fix X issues first"
- After clicking: button disabled, shows "Submitting..."

**Submit flow:**
1. User clicks Build button
2. JS validates all required fields
3. If validation passes: POST to `/designer/api/factions/<id>/request` with `{type: "build", prompt: "user prompt text"}`
4. Server creates queue file in ~/.cw-admin-queue/pending/
5. Agent picks up job from pending/, moves to running/
6. Terminal log entry created (via tlog-add) when agent starts
7. Agent completes work, writes summary and cost to terminal log
8. Job moves to done/ folder with .reply file

## COMMON PROBLEMS YOU SOLVE

**Problem: "Summary or cost not showing in terminal log"**
- Cause: You completed work but didn't update terminal log with summary and cost
- Fix: Add summary and cost to the terminal log entry:
  ```bash
  echo "Your work summary here" > /tmp/summary.txt
  python3 designer-admin.py tlog-summary <entry-id> /tmp/summary.txt
  python3 designer-admin.py tlog-cost <entry-id> <cost-in-usd>
  ```

**Problem: "How do I know if work is complete?"**
- Check the admin queue: `ls ~/.cw-admin-queue/done/<job-id>.reply`
- If .reply file exists but terminal log has no summary/cost, fill them in now

**Problem: "Image not showing in game"**
- Cause: Image uploaded to designer but not synced to game server
- Fix: Redeploy with `--assets` flag to sync images
- Verify: open a game with the faction, run example E3 (image loaded check) and E6
  (failed requests), screenshot the board/card and READ it. Fixed = 0 broken images
  for that faction AND the screenshot shows the art.

**Problem: "Wrong color / unreadable text / card looks broken in game"**
- Check: open the game, run E2 (screenshots) + E4 (computed colors), READ the
  screenshots. Compare to designer meta.color. Fix the overlay/CSS/build, redeploy,
  repeat the SAME screenshots, and report both before and after.

**Problem: "Validation won't let me submit"**
- Cause: Required field missing (abilityType if special ability checked, SB cost, etc)
- Fix: Identify missing fields via `checkMissing()`, tell user which to fill

**Problem: "My faction isn't in the picker"**
- Cause: Faction built but not added to faction picker arrays
- Fix: Add to both default picker AND alternate picker, redeploy

**Problem: "Terminal log is cluttered with old entries"**
- Solution: This is expected, do NOT delete old entries
- User can filter by design object, user, type, date
