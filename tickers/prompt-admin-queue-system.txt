Admin Queue System - Faction Designer Integration

This prompt documents the faction designer queue processing system.

20-MINUTE / 3-TRY LIMIT - STOP AND HAND OFF, DO NOT GRIND
═══════════════════════════════════════════════════════════════════════════

If you cannot solve this request within 20 minutes, OR you have tried and
failed 3 times (same error repeating, same approach not working), STOP.
Do not keep looping on the same approach.

Instead:
1. Take what you have done so far (partial fix, diagnosis, files touched).
2. Write a clear, short summary: what you tried, what worked, what is still
   broken, and your best guess at what to try next.
3. End your reply with that summary. Do not keep working past this point.

This hands the task to the next tier automatically (this queue escalates
Haiku -> Sonnet -> Opus on failure). The next agent that picks this up -
whether it is a Sonnet or an Opus run - has these SAME instructions: if IT
also can't solve it in 20 minutes or 3 tries, it stops and hands off the
same way, one tier up. Opus is the last tier; if Opus also hits the limit,
summarize plainly for the owner instead of continuing to retry.

SIMPLE UPDATE SECTION
═══════════════════════════════════════════════════════════════════════════

The Simple Update section allows designers to swap faction images WITHOUT requiring
a full code rebuild. This section should be populated for every faction with rows
for each swappable image asset.

WHEN TO POPULATE:
- Immediately after a faction's initial build is complete
- Before marking a faction as "built" in the designer

WHAT TO ADD:
For each faction (using faction acronym), add these rows to the Simple Update section:

1. <acr>-glyph.webp           # Faction glyph/symbol
2. <acr>-card.webp            # Faction card image
3. <acr>-spellbooks.webp      # Spellbook reference card
4. <acr>-acolyte.webp         # Acolyte/cultist unit image
5. <acr>-high-priest.webp     # High Priest unit image (if faction has one)
6. <acr>-<unit>.webp          # One row per custom unit

Examples:
- fm-glyph.webp
- fm-card.webp
- fm-spellbooks.webp
- fm-acolyte.webp
- fm-high-priest.webp
- fm-bone-sculptor.webp
- fm-muscle-stitcher.webp
- fm-body-architect.webp
- fm-screaming-wall.webp

For PRM:
- prm-glyph.webp
- prm-card.webp
- prm-spellbooks.webp
- prm-acolyte.webp
- prm-high-priest.webp
- prm-astral-egg.webp
- prm-celestial-fledgling.webp
- prm-ycgnagnnisssz.webp

For DGT:
- dgt-glyph.webp
- dgt-card.webp
- dgt-spellbooks.webp
- dgt-acolyte.webp
- dgt-conquest.webp
- dgt-pestilence.webp
- dgt-war.webp
- dgt-famine.webp
- dgt-death.webp

HOW IT WORKS:
- Designer uploads new image with matching filename
- System detects the file and swaps it in the webp/images folder
- Change appears in game immediately (no rebuild required)
- Assets are deployed via deploy-homebrew-to-vm.sh --assets

IMPORTANT NOTES:
- Simple Update section name may also appear as "Quick Update" in some docs
  (they are THE SAME SECTION)
- This is purely for IMAGE swaps - code changes still require full rebuild
- Unit info SVGs (webp/info/<acr>-<unit>.svg) are NOT in Simple Update
  (those are generated during build and rarely need swapping)

CLAUDE TERMINAL LOG - CHECKING AND RESPONDING TO ENTRIES
═══════════════════════════════════════════════════════════════════════════

The Claude Terminal Log is a live activity feed in the admin console that tracks
all designer work and admin agent activity. You MUST check this regularly.

**WHERE IT IS:**
- Designer service (on the VM): data/terminal-log.json
- Admin console tab: "Claude Terminal Log"
- CLI command: `python3 designer-admin.py terminal-log`

**HOW TO READ IT:**
Use the CLI tool to list all entries (returns JSON):
```bash
cd ~/Claude-Projects/cthulhu-wars-tools/tickers
python3 designer-admin.py terminal-log
```

This returns a JSON array of all entries with their IDs, types, users, and current status/summary.
For a quick count or grep: `python3 designer-admin.py terminal-log | grep -c '"id"'`

**ENTRY TYPES:**
- extract: Design extraction request (spellbook text, menu text, etc.)
- build: Faction build request
- bug: Bug fix request
- admin: Direct admin console submission (from /tmp/claude-prompts.log queue)

**WHEN TO CHECK:**
- At the START of every conversation turn
- When the owner asks about specific entry numbers (e.g., "check entries 111, 112, 113")
- After completing work to update the entry summary

**HOW TO UPDATE SUMMARIES:**
After completing work on an entry, update its summary:
```
cd ~/Claude-Projects/cthulhu-wars-tools/tickers
echo "Fixed X, deployed to Y, cache Z" > /tmp/summary.txt
python3 designer-admin.py tlog-summary <entry-id> /tmp/summary.txt
```

**HOW TO ADD COST:**
When work has a known cost (from agent runs):
```
python3 designer-admin.py tlog-cost <entry-id> <usd-amount>
```

**COMMON WORKFLOW:**
1. Owner says "check entry 123" or "what's in the terminal log?"
2. Run: `cd ~/Claude-Projects/cthulhu-wars-tools/tickers && python3 designer-admin.py terminal-log`
3. Parse the JSON to find entry with matching id or n (number)
4. Read the entry's prompt and summary
5. Do the requested work
6. Update the entry summary with results

**CRITICAL:**
- ALWAYS use `python3 designer-admin.py terminal-log` to read the log
- NEVER try to read terminal-log.json directly (it's on the VM, not local)
- Every admin queue submission creates a terminal log entry (type: admin, id: q_<queuefile>)
- Entry IDs starting with "q_" are admin console submissions
- Entry IDs starting with "r_" are designer extraction/build/bug requests

SPELLBOOK GUIDANCE INTEGRATION
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

The rebuild process automatically includes spellbook guidance for Claude:

1. DETECTION: When a faction has multi-power or multi-sided spellbooks,
   the designer server computes guidance via compute_spellbook_guidance()

2. FLAGS: Spellbooks are marked with:
   - dual=true (for multi-power on side A)
   - dualB=true (for multi-power on side B)
   - twoSided=true (for swappable sides A and B)

3. UI DISPLAY: In the designer, "Guidance for Claude" appears when:
   - At least one spellbook has dual=true OR
   - At least one spellbook has twoSided=true
   Shows both Multi-Power and Multi-Sided guidance sections as needed

4. CLAUDE RECEIVES: When build is submitted:
   - Design JSON includes spellbookGuidance field
   - Claude sees guidance in /designer/api/factions/<fid> endpoint
   - Admin queue agent includes guidance in build prompt
   - Guidance tells Claude about power slots, SBR count, overlay structure

5. FOR DGT SPECIFICALLY:
   - Gods' Scale and similar spellbooks need twoSided=true
   - Ensure no faction exceeds 6 SBR/SB slots on faction card
   - Multi-sided spellbooks = 2 connected SB slots, not 1+1
   - Use Dragon Ascending (one-use) or Daemon Sultans (Doom recharge) code templates

CLAUDE RECEIVES THIS GUIDANCE FOR ALL BUILDS:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Multi power Spellbooks:
Spellbooks with multiple powers on 1 spellbook side should be treated as a single spellbook. This includes but is not exclusive to:
- Faction card spellbook / SBR slots- no faction should EVER have more than 6 SBR/ SB slots on its faction card, unless you are explicitly told otherwise
- SBRs and availability of the powers- completing a single SBR can earn you a SB with 2 powers. That is still ONE spellbook. You earn BOTH powers at once.
- Spellbook overlays - clicking on a spellbook with 2 powers should bring up an overlay describing BOTH powers
- Moonbeast - blocking a 2 power spellbook with a Moonbeast blocks BOTH powers
- Copying a spell book (Nodens, not yet coded) - copying a 2 power spellbook copies BOTH powers

Multi sided Spelllbooks

Spellbooks with 2 spellbook sides that both have powers should be treated as 2 spellbooks, but generally 2 spellbooks that are connected and can be swapped out one for the other, per the explicit rules of that spellbook. NOT as 2 spellbooks that can each be taken independently. Leverage how the neutral spellbook "recriminations" works to code the swap out, but make sure it is strictly applied so that only "sides" of the same spellbook can be swapped out via this faction's swapping mechanism. (Recriminations will still apply and should still work- but will apply to swapping in a totally separate spellbook, not a separate "side" of the same spellbook").

Spellbooks that have 2 sides with powers can have a 3rd "face down" side. If the spellbook power says to flip it "face down" after use, it is either a use once power, or a use and recharge power. Its own rules should determine which. For a "use once" power, once used, it is blocked for the rest of the game. See opener of the way's "dragon ascending" for an example of this, and to copy its code. For a "use and recharge" spellbook, see any of daemon sultans spellbooks, to copy their code. They are flipped face down when used, and are flipped face up (recharged) in the doom phase. For a different "recharge" mechanism, see the Library Times associated with the Library at Celaeno Map. They can be "recharged" by spending a token associated with that map (silence tokens).

For a spell book with 3 total sides (2 with powers, one the "face down"/ powerless side), see the spell book rules for when (if) it is "recharged" whether it goes back to side 1 or side 2.
